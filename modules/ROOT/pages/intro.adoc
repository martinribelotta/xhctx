= Introduction and Motivation

[NOTE]
.Status
====
This is a first-draft, non-ratified specification of an experimental
RISC-V extension. It is not endorsed by RISC-V International. All CSR
addresses are placeholders pending allocation from the appropriate
custom/reserved range (see xref:csrs.adoc[Chapter 3], Section 3.1).
Sections marked _(Non-normative)_ are explanatory and impose no
conformance requirements.
====

== Overview

`Xhctx` ("Hart Context") replaces the classical interrupt model --

[source]
----
Event → Trap → ISR → mret
----

-- with a model in which events activate *persistent execution
contexts* that behave architecturally as RISC-V harts:

[source]
----
Event → Event Fabric → Persistent context → Abandonment → Next context
----

The unit of scheduling ceases to be the interrupt and becomes the
*hart*. Hart selection is performed entirely by hardware; no
programmable scheduler exists.

== Motivating Use Cases

[NOTE]
.Non-normative
====
This section is explanatory context for the design choices made
throughout this specification; it imposes no conformance requirements.
====

`Xhctx` was originally motivated by two demanding domains that, it
turns out, want the same thing from the hardware: mission-critical
aerospace systems, and high-speed network processing in FPGA fabrics.

Aerospace / mission-critical:: What xref:exception-delivery.adoc[Section 8.1]
calls "recovery is not resumption" for a faulted hart is, from this
angle, an ARINC-653-style partition boundary enforced by hardware
rather than by a hypervisor or partitioning kernel: a faulted hart
never silently continues, and even its strongest recovery tier
(xref:context-lifecycle.adoc[Section 7.2], Case F) is an explicit,
firmware-decided restart from a known-good state, not an implicit
continuation -- fewer
software layers to certify to sustain isolation between subsystems of
different criticality on the same core. Bubble-free one-cycle
activation and a precise preemption boundary
(xref:priority-preemption.adoc[Chapter 6]) give a WCET argument that
does not depend on how many registers a given ISR happens to touch.
And a fixed-priority hardware arbiter is a far smaller, more
exhaustively verifiable artifact than a general RTOS scheduler --
shifting scheduling from software certification territory (e.g.
DO-178C) into hardware certification territory (e.g. DO-254).

High-speed network processing in FPGA fabric:: Mandatory bypass
(xref:software-events.adoc[Chapter 5]) dispatches on the cycle after
an event with no software polling -- necessary to react to
"descriptor ready" or "packet arrived" at line rate. Independent
flows, DMA rings, or virtual channels map naturally onto separate hart
contexts, arbitrated by fixed priority (e.g. QoS class as `ctx_id`
priority). Specific to FPGA targets: this is one physical pipeline
plus `N` banked register files (cheap in BRAM), instead of `N` fully
duplicated soft-core pipelines (expensive in LUTs/DSPs) to handle `N`
independent handlers -- with the ergonomics of C instead of
hand-written FSMs.

== Goals

An `Xhctx`-compliant implementation SHALL provide:

* Deterministic, minimal-latency hart activation.
* Zero software-managed register save/restore across hart switches.
* No ISR prologue/epilogue.
* No use of `mret` as a control-transfer mechanism.
* Hart state resident entirely in hardware.
* A hardware-arbitrated Event Fabric with fixed-priority arbitration.
* A viable implementation on a small RV32E core.

== Design Principles

. Harts are persistent: they are never created or destroyed during
  operation.
. Events activate harts; no ephemeral ISRs exist.
. Software never writes the currently active hart selector directly.
. All execution state is fully banked, one copy per hart.
. A hart switch consists solely of selecting a different bank.
. Hart selection is arbitrated entirely by hardware; no RTOS-style
  programmable scheduler exists.
. Behavior is deterministic and formally verifiable, modulo the
  documented trade-offs in xref:priority-preemption.adoc[Chapter 6].
. The ISA remains compatible with RV32E wherever possible
  (xref:compatibility.adoc[Chapter 10]).
