= Reference Microarchitecture

[NOTE]
.Non-normative
====
This entire chapter is non-normative reference material; it imposes no
conformance requirements.
====

Target RTL:

* RV32E, 3-stage pipeline, 16 harts
* Fully banked register file and pipeline state
* 16 FIFOs
* Priority encoder
* Mandatory event bypass
* One-cycle target hart activation
* `ctx_id` tag propagated through IF/ID, ID/EX, EX/WB
* `mepc[ctx_id]` / `mcause[ctx_id]` banks
* Per-hart mask bit feeding the priority encoder (debug support,
  xref:debug-support.adoc[Chapter 12])
* Per-hart, individually-addressable reset-vector-load and
  pipeline-invalidate enables (Case F restart,
  xref:context-lifecycle.adoc[Section 7.2])
* Each hart exposed as an independent hart to the standard RISC-V
  Debug Module, reusing its existing multi-hart infrastructure

== Pipeline banking and the zero-bubble switch

Banking is not limited to the register file: the pipeline registers
themselves (IF/ID, ID/EX, EX/WB) are instantiated once per hart, and
the shared combinational datapath (decode, ALU, load/store sequencing)
is time-multiplexed across those banks by `active_ctx`. Register reads
and writes are addressed directly by `{ctx_id, reg_num}`, so no read or
write port ever conflicts between harts.

Because the latches themselves are banked, no per-instruction tag needs
to travel through the pipeline to route WB writes correctly: in any
given cycle, every stage is necessarily operating on the same bank --
whichever one `active_ctx` currently selects -- so the destination is
never ambiguous.

A hart switch (voluntary via `mctxctl`, or forced by arbitration) is a
*bank-select switch*, identical in cost to a jump resolved in a single
cycle: `active_ctx` changes, and the shared datapath begins reading and
writing the incoming hart's own latches instead of the outgoing hart's.
Nothing is squashed and nothing is lost -- the outgoing hart's
in-flight, not-yet-retired instructions (whatever was sitting in its
IF/ID, ID/EX, or EX/WB latch) are simply frozen in its own bank,
untouched, until that hart is reactivated, at which point they resume
exactly where they left off. This requires `mctxctl` (and any
hardware-forced switch condition) to resolve within a single pipeline
stage. Under that constraint, hart activation is *one cycle, no
bubble* -- not a stall-based drain, and not a discard-and-refetch.

The shared execution units (ALU, multiplier, load/store port) are
*not* banked -- only the per-stage latches are -- which is why a
multi-cycle operation is never preempted mid-flight
(xref:priority-preemption.adoc[Section 6.3]): the unit it occupies has
only one instance, and cannot serve two harts in the same cycle.

== Restart reuses the reset datapath

Case F (xref:context-lifecycle.adoc[Section 7.2]) is the one switch
that deliberately discards a bank's content instead of preserving it.
It needs no new datapath to do so: power-on reset already has to load
`RESET_VECTOR` into every hart's `PC` bank and invalidate every
pipeline latch, broadcast to all 16 banks at once. Case F is the same
load and the same invalidate, narrowed from a global broadcast to a
single, `target_ctx_id`-selected bank -- a 16-way enable demux on
signals that already exist, not a new write port. The only other new
logic is `mctxctl`'s opcode decode (xref:csrs.adoc[Section 3.6]) and
the pulse that sets `waiting[target_ctx_id]`, reusing the same bit
every other wakeup already sets. No change to the priority encoder,
the FIFOs, or the bank-select mux itself is required: `target_ctx_id`
simply becomes a normal contender for `next_ctx` on the cycle after
the restart, indistinguishable from any other Case B wakeup.
